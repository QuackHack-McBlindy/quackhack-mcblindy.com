The Dotfiles Workflow

Two commands, one tag, four sounds. Every change starts with yo switch on my own machine, or yo deploy to another host. Both end in yo push — which auto-generates the README, commits, tags the NixOS generation, and force-pushes to GitHub, where CI runs nix flake check. And if it all goes sideways, yo rollback brings the host back to any past tag.

yo switch local rebuild
test or save
yo deploy remote rebuild
bootstrap + watchdog
yo push commit + tag + push
then CI verifies
yo rollback when it goes wrong
back to gen N

 ── PIPELINE ──
 set -o pipefail
 cmd 2>&1 | tee $BUILD_LOG | nom --json
          │
          └──► raw log kept for error extraction

 ── ON SUCCESS ──
 ✅  play_win

 ── ON FAILURE ──
 fail_count += 1
 fetch_nix_error_log  (nix log $drv | tail -100)
 fail_count ≥ 5   ──►  ❌  play_fail2
 else             ──►  ❌  play_fail
 exit 1
Why this is nice: yo rb never touches the saved system generation — if the new config breaks the desktop you're still logged into, just reboot and you're back on the old one. yo rb ! does the same build but commits it, which is exactly what you want when the test passed and you're ready for it to persist.

yo deploy

— remote rebuild
~/dotfiles $ yo deploy -h 
   yo deploy

  Build and deploy a NixOS configuration to a remote host. Bootstraps, builds
  locally, activates remotely, and auto-tags the generation.
  Usage:  yo deploy [OPTIONS]

   ▶ Parameters

   --host
  Host machine to build and activate

   --flake
  Path to the directory containing your flake.nix
  (optional) (default: /home/pungkula/dotfiles)

   --user
  SSH username
  (optional) (default: pungkula)

   --repo
  Repository containing containing your NixOS configuration files
  (optional) (default: git@github.com:QuackHack-McBlindy/dotfiles.git)

   --port
  SSH port
  (optional) (default: 2222)

   --test
  Test deployment, does NOT save system generation, no git push, reboot to
  revert
  (optional) (default: false)

   --watchdog
  Wether to activate watchdog timer on target
  (optional) (default: false)

   --watchdog-timer
  Minutes on watchdog-timer.
  (optional) (default: 5)

   --all
  Build all - deploy all
  (optional) (default: false)

  ## Voice Commands

  Patterns: 54
  Phrases: 792
  Ratio: 14
~/dotfiles $ yo deploy homie 
 yo deploy <host>          real deploy  (auto yo push)
 yo deploy <host> !        test deploy  (watchdog + no push)

 ── PRE-FLIGHT ──
 host ∈ nixosConfigurations
 ssh reachable  (5 s timeout)
 [test + --watchdog]  arm rollback timer:
        systemd-run --on-active=5min
        --unit=nixos-test-watchdog-$$

 ── BOOTSTRAP (only if $flake/.git missing) ──
 convert_git_to_https  git@host:x.git → https://host/x.git
 git clone $https_repo $flake      (on remote)
 yo yubi decrypt secrets/hosts/<host>/age.key
      ──► ssh cat > $key_path.tmp
      ──► chmod 600 · chown root
 add --build-host $user@$host      (remote build next)

 ── BUILD + SWITCH ──
 nixos-rebuild { test | switch }
      --flake $flake#<host>
      --target-host $user@$host
      --ask-sudo-password
      --option builders ""
      --show-trace

 ── VERIFY (test only) ──
 sleep 6
 ssh ok?   ──►  cancel watchdog  ──►  ✅ play_win
 lost?     ──►  let watchdog reboot  ──►  ❌ play_fail

 ── POST (real only) ──
 GEN_NUM = ssh "sudo -n nix-env --list-generations"
             | awk '/current/'
 yo push --host $host --generation $GEN_NUM
The important bit: yo deploy <host> ! arms a one-shot systemd-run timer on the remote that reboots it in --watchdog-timer minutes. If the reboot works, the SSH check at the end cancels the timer. If the deploy bricks networking or the login shell, the host reboots itself back to the previous generation — no rescue shell, no trip to the machine.

CI

— after the push lands
.github/workflows/nix-build.yml 
name: Nix build

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 120
    steps:
      - uses: actions/checkout@v4
      - uses: DeterminateSystems/determinate-nix-action@v3

      - name: Free disk space
        run: |
          sudo rm -rf /usr/share/dotnet /usr/local/lib/android /opt/ghc \
                      /opt/hostedtoolcache/CodeQL || true
          df -h /

      - uses: DeterminateSystems/flake-checker-action@v9

      - name: nix flake check
        run: nix flake check --system x86_64-linux --keep-going --accept-flake-config
What's happening: yo push lands on main — no PR gate for a personal dotfiles repo. CI then runs nix flake check on the pushed commit with --keep-going, so a broken one-liner in module.nix fails the run instead of failing the next yo rb on your machine.

yo rollback

— the escape hatch

When the new generation is broken, when CI fails, or when you just need yesterday's config back: yo rollback lists every tagged generation for a host, lets you pick one, checks out the matching commit on the remote, and activates that NixOS generation. One prompt, one command, back to a known-good system.

~/dotfiles $ yo rollback -h 
   yo rollback

  Rollback a host to a previous NixOS generation. Fetches Git tags and reverts
  system+config to a synced, tagged state.
  Usage:  yo rollback [OPTIONS]

   ▶ Parameters

   --host
  Host to rollback

   --flake
  Path to the directory containing your flake.nix
  (default: /home/pungkula/dotfiles)

   --user
  SSH user
  (optional) (default: pungkula)
~/dotfiles $ yo rollback homie 
 yo rollback <host>          pick a generation, restore it

 ── LOCAL ──
 git fetch --tags --force
 git tag -l "<host>-generation-*" --sort=-v:refname
      │
      └──►  Generation 47:  (Tue Nov  9 22:15:12 2026) Autocommit: Generation 47
            Generation 46:  (Mon Nov  8 19:04:33 2026) Autocommit: Generation 46
            Generation 45:  (Sun Nov  7 11:22:50 2026) Autocommit: Generation 45
            ...

 read -p "Enter generation number: " GEN_NUM
 TAG_NAME="<host>-generation-$GEN_NUM"

 ── REMOTE ──  (ssh bash -s -- $flake $TAG_NAME $GEN_NUM)
 git fetch --tags --force
 git rev-parse "$TAG_NAME"       ← verify tag exists on remote
 git checkout "$TAG_NAME"        ← detach HEAD at the tagged commit
 sudo /etc/profiles/per-user/$user/bin/rollback "$GEN_NUM"
      │
      └──►  system profile switches to generation $GEN_NUM
            and that generation is activated

 echo "Remote rollback to generation $GEN_NUM complete!"
Why tagging is worth the effort: Without yo push's tags, this would be manual: SSH in, run nix-env --list-generations, cross-reference with git log to find the matching commit, git checkout that commit by hand, then nix-env --switch-generation and activate. With the tags, it's one prompt. The tag <host>-generation-<N> is the contract between the running system and a specific commit — and yo rollback is what honors it.
⚠️ Heads-up: after the remote git checkout $TAG_NAME, HEAD is detached at the tagged commit. That's fine for reproducibility — the host is now running exactly the config from that tag. But a subsequent yo deploy on that host should be done from your local machine (which is still on main), not from inside the remote checkout. Otherwise you'd be deploying from a stale snapshot.

Three things that make it worth using

These are the parts I'd miss if I switched to another framework.

🚀

Bootstrap

Bare metal to a running system, one command. No manual git clone, no copying keys over by hand.

  • Detects if $flake/.git exists on the target — safe to run every time.
  • Auto-converts the SSH repo URL to HTTPS for the initial clone (no key yet on the remote).
  • Decrypts the host's age.key locally — Yubikey tap required.
  • Streams the key to the remote via ssh cat >, chmod 600, chown root — never touches disk unencrypted.
  • Switches to --build-host on first deploy, because the signing key only lives on the target.
  • On the second deploy, the key is already there — falls back to building locally and only pushing the closure.
📚

update-readme

The README isn't hand-maintained. It's generated from config at build time, then refreshed on every yo push.

  • YO_DOCS — full CLI reference from config.yo.scripts, voice-ready ✅ / not 📛, one row per script.
  • USER · HOST · THEME — three config blocks rendered to Nix via jq.
  • DEVICES_SCENES — Zigbee devices, scenes, TVs, channels from config.house.*.
  • SMARTHOME — the full modules/myHouse.nix file embedded.
  • TREE — nix flake show with ANSI codes stripped.
  • FLAKE — the full flake.nix inline.
  • CONTACT — Matrix / Discord / Email badges, only shown if the config has them.
  • Plus version badges: NixOS · Linux · Nix · bash · GNOME · Python · Rust · Mosquitto · Pokémon total.
  • Zero network, zero CI — runs sed + awk against markers in an already-checked-out README.
🏷️

Generation tagging

Every working system has a git tag. You can check out the exact commit that produced generation N on host X — months later.

  • Reads the current generation number from sudo nix-env --list-generations after the switch.
  • Tags it <host>-generation-<N> — e.g. homie-generation-47.
  • Force-moves the tag if you rebuild the same generation (idempotent — the tag always points at the current commit for that gen).
  • Force-pushes branch + tags, so CI always sees the exact state that produced the running system.
  • Reproduce a running system: git checkout <host>-generation-<N> && nixos-rebuild switch --flake .#<host>.
  • Consumed by yo rollback — one prompt to go back to any past tagged generation. See the recovery section above.
